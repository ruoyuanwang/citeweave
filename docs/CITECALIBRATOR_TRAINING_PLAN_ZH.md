# CiteCalibrator-8B 训练与评测方案

> 版本：v1.1
> 日期：2026-09-07
> 状态：实验设计稿
> 适用算力：2–4 张 RTX 4090（24 GB/卡）

> **执行前置门禁：** 本文不是立即开训授权。必须先按 `docs/CITECALIBRATOR_BENCHMARK_HANDOFF_ZH.md` 完成自然分布 Discovery Bench，并同时通过问题规模、非训练基线缺口、任务可解性和实际价值四类门禁，才进入本文的数据扩展与训练阶段。

## 1. 先把方案说清楚

### 1.1 一句话方案

保留前沿 API 负责写文章，另外训练一个 8B 小模型，专门检查文章中由图计算和文献证据导出的高风险论断；它不重写整篇文章，只判断一句话能否被现有证据支持，并在有问题时进行最小修订。

### 1.2 为什么项目需要这个模型

本项目已经能够通过 Agent 调用检索、图构建、路径分析、社区分析、时间切片和鲁棒性检验，再由云端大模型把结果写成文章。真正的薄弱环节不是“文章写不出来”，而是从计算结果到自然语言论断的最后一步容易出现语义越界。

例如，程序实际得到的是：

> 在当前语料、边权阈值为 3 的共现图中，A 位于 B 与 C 之间的最短路径上；当阈值改为 5 时，该路径不再存在。

通用模型可能写成：

> A 是连接 B 与 C 两个研究方向的关键机制。

这句话至少发生了三次越界：

1. 把特定图和特定参数下的结构现象写成普遍结论；
2. 把“位于路径上”升级为“连接两个研究方向”；
3. 把网络结构关系升级为领域中的“关键机制”。

数字、实体和引用可能都是真的，因此传统关键词规则很难完整发现问题；通用 API 即使被要求自检，也可能受到自己刚刚生成的表述影响，并且不一定稳定理解图算法、参数扰动和证据边界之间的关系。

训练专用模型的必要性来自本项目拥有一类通用模型没有被专门训练使用的信号：

- 图程序的精确输入和执行结果；
- 节点、边、社区、路径等对象的语义定义；
- 每个结论对应的原始文献和来源链；
- 改变阈值、时间窗、随机种子后的稳定性结果；
- 哪些自然语言解释被程序结果允许，哪些不被允许。

这些信号可以大规模、低成本地产生可验证监督，从而训练一个“小而专”的模型。创新点不是用 8B 模型正面对抗数十亿甚至更大规模的云端模型，而是用项目独有的数据，让 8B 模型在一个边界明确的专门任务上超过通用 API 自检。

### 1.3 为什么不训练文章生成模型

2–4 张 RTX 4090 可以高质量地完成 8B 模型的 QLoRA 微调，但无法从头训练具备广泛知识和写作能力的通用模型。即使把 8B 模型微调成文章生成器，它在知识覆盖、长文本规划和语言表达上大概率仍不如现有前沿 API。

因此合理分工是：

| 模块 | 使用什么 | 原因 |
|---|---|---|
| 检索、图分析与实验执行 | 现有 Agent 和确定性程序 | 可追溯、可回放 |
| 文章规划与初稿 | 前沿 API | 通用知识和长文本表达更强 |
| 高风险论断校准 | 训练后的 8B 专用模型 | 任务窄、监督精确、可本地批量推理 |
| 极低置信度样本 | 人工或更强 API | 避免小模型强行判断 |

### 1.4 最终要得到什么结果

预期产物不是一个可以独立完成所有工作的“小号大模型”，而是以下三个可复用成果：

1. **CiteCalibrator-8B 模型**：输入论断和证据包，输出保留、限制、拒绝或放弃判断，以及最小修订文本；
2. **CiteClaim-Calib 数据集**：包含可执行结果、参数扰动、来源链和人工裁决的论断校准数据；
3. **Agent 集成模块**：自动抽取高风险论断、调用校准器并只重写受影响位置。

理想效果是：文章中过度推断和错误引用明显减少，而正确内容、领域细节和可读性基本保持；与此同时，校验阶段的 API 调用次数和人工审核量下降。

### 1.5 本方案的核心配置

- 训练对象：8B 级论断校准器，而不是通用文章生成器；
- 推荐基座：Qwen3-8B-Instruct，使用 4-bit QLoRA；
- 训练路线：SFT → DPO → 概率校准；
- 数据路线：程序生成事实与受控反例，API 只扩充语言表达，人类校准边界并建立最终金标准；
- 数据规模：25,000–35,000 条 SFT 样本、25,000–40,000 对 DPO 数据；
- 人工规模：600–1,000 条训练校准样本、400 条开发集、800 条双人标注最终测试集；
- 算力策略：一个 8B QLoRA 任务使用一张 4090，多张卡并行运行随机种子和消融；
- 成功标准：不仅要超过未训练的 8B，还要超过“前沿 API 自检”和“API + 现有规则”。

## 2. 模型的具体作用与边界

### 2.1 模型在系统中做什么

模型名称暂定为 **CiteCalibrator-8B**，训练方法暂定为 **PGCA（Program-Grounded Claim Calibration）**。对每一条被筛出的高风险原子论断，它完成四件事：

1. **支持性判断**：判断论断是否被程序结果和文献证据支持；
2. **风险定位**：指出问题属于数字、实体、路径、来源、范围、因果或参数稳定性等哪一类；
3. **证据对齐**：给出真正支持判断的 evidence ID，避免“有引用但引用不支持”；
4. **最小修订**：尽量保留正确内容，只修改越界的局部表达。

四种决策的实际含义是：

| 决策 | 什么时候使用 | 系统动作 |
|---|---|---|
| supported | 事实和表述边界均有支持 | 原句保留 |
| qualify | 核心事实正确，但范围、因果或稳定性表述过强 | 使用最小修订替换原句 |
| reject | 核心事实错误或引用不支持，轻微修改无法挽救 | 删除或交给生成模型重写 |
| abstain | 证据缺失、冲突或超出模型可靠范围 | 转人工或更强 API |

### 2.2 校验哪些句子

不是给文章中的每句话都做一次完整校验。先由规则和 Claim Extractor 找出高风险句，再拆成原子论断。重点处理：

- 含数值、排名、年份、实体关系或路径的论断；
- 来自文献图、引文图、共现图或社区分析的论断；
- 含“导致、驱动、证明、关键机制、核心原因”等因果或机制措辞的论断；
- 对总体、领域或长期趋势作外推的论断；
- 对参数变化敏感或证据不足的论断。

纯过渡句、文章组织句、无实证含义的表达不进入校准器。一般性领域知识如果没有对应证据包，也不应让模型仅凭参数记忆判断，应转为 `abstain` 或交由独立事实核查模块处理。

### 2.3 模型不做什么

- 不负责检索新文献；
- 不执行图算法；
- 不判断输入程序本身是否符合用户真正意图；
- 不基于自身记忆补充新的领域事实；
- 不独立生成整篇文章；
- 不替代最终的专家审查；
- 不把相关性证明成因果性。

这些边界非常重要。边界越窄，2–4 张 4090 训练出的模型越可能在目标任务上形成真实、可复现的优势。

### 2.4 一个完整示例

假设输入证据显示：A 在阈值 3 时是 B 与 C 的桥接节点，但阈值 5 时该结论消失，且文献只描述 A 与 B 的共现关系。

候选论断：

> A 是驱动 B 与 C 两个研究方向融合的核心机制。

期望输出：

```json
{
  "decision": "qualify",
  "risk_types": [
    "causal_overclaim",
    "semantic_reification",
    "parameter_sensitivity_omitted"
  ],
  "unsupported_spans": ["驱动", "核心机制"],
  "evidence_ids": ["E_graph_17", "E_source_04"],
  "revised_claim": "在当前语料构建、边权阈值为 3 的共现图中，A 表现为连接 B 与 C 的桥接节点；该结构关系在更高阈值下不稳定。",
  "required_limitation": "该结果描述网络结构，不构成领域因果机制证据。",
  "confidence": 0.91
}
```

这个例子体现了模型真正要学习的内容：不是记住 A、B、C 的知识，而是学会从程序证据、参数稳定性和语义契约约束自然语言表述。

## 3. 预期效果与创新定位

### 3.1 预期效果

预期效果分为三个层级：

| 层级 | 预期变化 | 不能接受的伪提升 |
|---|---|---|
| 论断级 | 更准确地区分 supported、qualify、reject、abstain | 通过全部预测 reject 获得表面安全性 |
| 文章级 | 明显减少因果夸大、范围外推和来源错配，同时保留正确信息 | 把文章改得空泛、机械或缺少领域细节 |
| 系统级 | 减少 API 自检调用和人工复核量，输出更稳定 | 只改善 JSON 格式，不改善研究质量 |

该模型不会在通用问答和文章写作上超过前沿 API。合理的成功定义是：在本项目定义的“有程序证据的图研究论断校准”任务上，专用模型优于同尺寸未微调模型，并在关键指标上达到或超过前沿 API 自检；集成后，整个 Agent 系统优于没有校准器的版本。

在正式实验前可把下表作为立项目标。它们是需要实验验证的目标，不是预先宣称的结果：

| 维度 | 目标值 |
|---|---|
| 相对未微调 8B | 四分类 macro-F1 至少提高 5 个百分点 |
| 高风险错误发现 | 过度推断召回率达到 0.85 以上 |
| 正确信息保护 | supported 误拒率不超过 0.10，数字与实体保留率达到 99.5% |
| 相对 API 原文 | 每 1,000 字过度推断数相对下降至少 30% |
| 相对 API + 规则 | 在错误发现或人工转交率上获得显著增益 |
| 文章可用性 | 正确且有支持的论断数非劣，容忍界限为 2 个百分点 |
| API 成本 | 校验阶段的 API token 消耗目标下降 50% 以上 |

若只达到前两项，却明显损害正确信息和文章可用性，模型不应被视为成功。

### 3.2 可形成的论文贡献

若实验成功，可形成三项相互支撑的贡献：

1. **数据贡献**：CiteClaim-Calib，一个由图程序执行结果、证据来源、参数扰动和人工裁决共同构成的论断校准数据集；
2. **方法贡献**：PGCA，利用可执行证据和扰动一致性监督训练专用论断校准模型；
3. **系统贡献**：证明“前沿 API 负责生成 + 小型专用模型负责校准”的组合，在质量、成本和可控性上优于 API 单独生成或自检。

### 3.3 研究假设

- H1：SFT 后的 CiteCalibrator 在未见主题上显著优于同基座 zero-shot 和 few-shot；
- H2：加入参数扰动和 provenance 后，模型对范围夸大、参数敏感性遗漏和来源错误的识别显著提升；
- H3：DPO 提升最小修订质量，而不会显著提高正确论断误拒率；
- H4：API + CiteCalibrator 在文章级过度推断率、成本或人工复核量上优于 API、API 自检和 API + 规则。

### 3.4 研究问题

- RQ1：可执行程序产生的弱监督，能否提升论断支持性判断？
- RQ2：参数扰动和来源监督，是否带来超越普通事实核查训练的增益？
- RQ3：专用校准器与通用 API 组合，是否优于 API 单独生成、API 自检和规则校验？

## 4. 系统工作流与代码边界

### 4.1 推荐工作流

```text
用户问题
  ↓
Graph Program / Agent 规划与执行
  ↓
结构化结果 + provenance + perturbation profile
  ↓
前沿 API 生成文章草稿
  ↓
Claim Extractor 抽取高风险原子论断
  ↓
CiteCalibrator-8B
  ├─ supported：保留
  ├─ qualify：最小降级或补充限制条件
  ├─ reject：删除或重新生成
  └─ abstain：提交人工或调用更强 API
  ↓
按论断依赖关系进行局部修订
  ↓
最终文章
```

### 4.2 与现有代码的关系

训练数据生成器应复用现有项目中的任务定义和结果结构，但不得修改已经冻结的正式实验：

- `src/citeweave/graph_discovery.py`：图任务和候选发现逻辑；
- `src/citeweave/operator_verification.py`：算子结果校验；
- `src/citeweave/graph_robustness.py`：鲁棒性与参数敏感性；
- `src/citeweave/article_quality_controls.py`：文章级质量控制；
- `src/citeweave/feedback_repair_trial.py`：反馈修订实验；
- `src/citeweave/article_claim_review.py`：论断审查与拆分逻辑。

训练扩展应建立独立的数据目录、实验配置和结果目录。当前 frozen formal v3 中已参与开发判断的主题只能用于兼容性诊断，不得作为最终无偏测试集。正式结论应使用全新、锁定且未参与训练设计的主题。

## 5. 输入与输出定义

### 5.1 输入结构

每个样本以一个原子论断为中心，建议采用以下 JSON 结构：

```json
{
  "question": "研究问题",
  "local_context": "论断所在段落及必要上下文",
  "candidate_claim": "待校验的原子论断",
  "graph_scope": {
    "dataset": "数据集标识",
    "node_semantics": "节点含义",
    "edge_semantics": "边含义",
    "time_range": [2015, 2025],
    "filters": {}
  },
  "operator_trace": {
    "program": [],
    "parameters": {},
    "execution_result": {}
  },
  "evidence": [
    {
      "evidence_id": "E1",
      "source_id": "source identifier",
      "content": "支持当前判断所需的最小证据",
      "provenance": {}
    }
  ],
  "perturbation_profile": {
    "stable_dimensions": [],
    "unstable_dimensions": [],
    "results": []
  },
  "interpretation_contract": {
    "allowed": [],
    "forbidden": [],
    "required_limitations": []
  }
}
```

### 5.2 输出结构

模型必须使用受约束的 JSON 输出：

```json
{
  "decision": "supported | qualify | reject | abstain",
  "risk_types": ["scope_overclaim"],
  "unsupported_spans": ["说明未被支持的文本片段"],
  "evidence_ids": ["E1"],
  "revised_claim": "保留原意的最小修订；supported 时可原样返回",
  "required_limitation": "必须补充的范围、参数或不确定性说明",
  "confidence": 0.86
}
```

其中：

- `supported`：事实、范围、措辞和证据均充分；
- `qualify`：核心信息成立，但必须降低确定性或补充限制条件；
- `reject`：核心事实或推断不成立，不能通过轻微修改保留；
- `abstain`：证据冲突、输入缺失或超出模型可靠判断范围。

### 5.3 风险标签体系

第一版建议固定以下多标签分类：

```text
numeric_error
entity_error
path_error
provenance_error
missing_evidence
scope_overclaim
causal_overclaim
semantic_reification
parameter_sensitivity_omitted
temporal_instability_omitted
community_instability_omitted
graph_construction_omitted
corpus_scope_omitted
unsupported_domain_mechanism
conflicting_evidence
unanswerable
```

标签说明和正反例必须在数据生产前冻结。训练中不得用“看起来不严谨”等不可操作的模糊标签代替上述定义。

## 6. 数据构造方案

### 6.1 数据集划分原则

实验单元必须按“主题/语料库”划分，而不是随机拆分论断。否则同一张图、相同实体和相似模板会同时出现在训练集与测试集，造成严重泄漏。

正式版建议：

| 划分 | 主题数 | 用途 |
|---|---:|---|
| Train | 30–40 | 生成 SFT 与偏好数据 |
| Dev | 5 | 阈值、提示词和超参数选择 |
| Internal Test | 5 | 迭代期间的内部验证 |
| Final Locked Test | 8 | 论文最终结果，完成前不可查看标签分布 |

MVP 可先采用 12/3/4 个主题的 Train/Dev/Test 划分。正式测试主题必须是在方法、标签规则和模型选择完成后才锁定的新主题。

主题应覆盖医学与生命科学、材料与能源、环境科学、计算机科学、农业、社会科学和交叉学科。候选主题需满足：

- 至少约 2,000 条身份校验通过的有效记录；
- 能构造有意义且非退化的图；
- 年份跨度足够支持时间切片；
- DOI、OpenAlex ID 或其他主键可追溯；
- 不同领域之间实体和术语重叠有限。

### 6.2 基础 ClaimCase 生成

每个基础案例包含以下生命周期：

1. 选择主题图和一个或多个锚点实体；
2. 从任务库采样图程序及参数；
3. 执行程序并保存完整结果、来源和软件版本；
4. 使用确定性模板生成 canonical claim；
5. 运行参数扰动，生成稳定性画像；
6. 根据 interpretation contract 生成正确标签与必要限制；
7. 由 API 仅做语言改写，扩充表达形式；
8. 生成单点受控错误和偏好对；
9. 通过自动质量门禁；
10. 对抽样、边界样本和最终测试集进行人工审核。

基础任务建议包括：

| 任务 | 目标基础案例数 | 典型风险 |
|---|---:|---|
| multi_hop_connector | 1,500 | 路径错误、关系夸大 |
| bridge_counterfactual | 1,000 | 反事实、因果化表达 |
| hub_removal_resilience | 1,000 | 鲁棒性和范围外推 |
| community_role_contrast | 1,000 | 社区实体化、随机性忽略 |
| temporal_structural_shift | 1,000 | 时间趋势、时间窗敏感性 |
| productivity_centrality_divergence | 500 | 指标语义混淆 |
| 简单查询与负控 | 1,000 | 数值、实体、边数量核对 |
| **合计** | **7,000** | — |

每张图应采样多个锚点和多个程序配置，避免模型把主题名称或固定实体当作标签捷径。

### 6.3 参数扰动设计

“鲁棒/不鲁棒”不能只是单一布尔值。每个案例应记录多维扰动画像：

- 边权阈值：2、3、5 等合理取值；
- 边随机删除：1%、5%，至少 3 个随机种子；
- 候选集上限、最短路径约束和图规模变化；
- 社区发现随机种子和 resolution；
- 时间窗宽度：2、3、4 年；
- 时间窗起止点平移；
- 身份映射、来源缺失和 provenance 错配模拟。

扰动结果至少包含：结论是否保持、数值变化幅度、排名变化、路径是否存在、社区归属一致性、证据集合变化以及需要写入文章的限制条件。

### 6.4 正样本构造

正确论断必须首先由程序结果和确定性模板生成。模板负责事实槽位和限定条件，API 只能改写表达方式，不能决定金标签。

每个 canonical claim 建议生成 2–4 种语言变体：

- 简洁事实表述；
- 学术写作表述；
- 带局部上下文的自然段内表述；
- 使用同义表达但保持相同证据边界的表述。

改写完成后必须重新抽取数字、实体、关系、时间范围和限定词，与 canonical claim 自动比对。

### 6.5 负样本与边界样本构造

负样本应采用“一次只改变一个因素”的受控变异，确保错误原因明确且可以自动验证。建议比例：

| 变异类型 | 比例 | 示例 |
|---|---:|---|
| 事实错误 | 15% | 修改数值、排名、年份、实体或路径 |
| 来源错误 | 15% | 引用不支持当前论断的来源 |
| 范围夸大 | 20% | 从局部样本外推到整个领域 |
| 因果夸大 | 15% | 将关联、桥接或时间先后写成因果 |
| 忽略参数敏感性 | 15% | 删除阈值、随机性或时间窗限制 |
| 语义实体化 | 10% | 把算法社区写成真实学派或机制 |
| 不可判断/冲突 | 10% | 删除关键证据或注入相互冲突证据 |

每条变异记录以下 lineage：原始案例 ID、变异操作、变异前后槽位、预期标签、预期风险类型和自动验证结果。

`qualify` 是最重要也最难的类别。它不应通过简单加入“可能”“或许”批量生成，而应由真实的不稳定性、适用范围或解释约束触发，并给出具体限制条件。

### 6.6 数据规模

正式 SFT 数据建议约 30,000 条：

| 类别 | 建议数量 |
|---|---:|
| supported | 8,000 |
| qualify | 9,000 |
| reject | 9,000 |
| abstain | 4,000 |
| **合计** | **30,000** |

DPO 数据建议 25,000–40,000 对。每对数据的 chosen 与 rejected 应尽量只在一个关键维度上不同，例如：

- 正确的最小修订 vs 机械地加入模糊词；
- 保留可支持信息 vs 整句删除；
- 明确参数限制 vs 忽略不稳定性；
- 使用正确 evidence ID vs 虚构引用；
- 合理 abstain vs 无证据强行判断。

MVP 阶段可先构造约 8,000 条 SFT 样本和 10,000 对 DPO 数据，用来验证任务是否可学、标签是否稳定以及专用模型是否超过强基线。

## 7. 如何保证数据质量

### 7.1 机器生成与人工审核的分工

推荐方式确实是“机标 + 人工审核”，但不是让大模型直接生成标签，再由人随便抽查。

- 程序负责：可执行事实、图结果、参数扰动、证据来源和受控错误；
- API 负责：语言改写、难例候选和表达多样性；
- 人类负责：规则制定、边界判断、语义合理性、领域解释和最终金标准；
- 专家负责：高风险领域样本、分歧仲裁和最终文章评价。

### 7.2 自动质量门禁

训练数据入库前必须通过以下检查：

1. **Schema 校验**：字段完整、枚举合法、JSON 可解析；
2. **身份校验**：实体 ID、来源 ID 和图节点一致；
3. **程序回放**：使用保存的输入和版本可重新得到相同结果；
4. **来源校验**：每个 evidence ID 可追溯，且属于当前语料范围；
5. **槽位一致性**：数字、实体、路径、年份和社区属性与执行结果一致；
6. **单变异隔离**：负样本除目标变异外，不得引入第二个实质错误；
7. **去重**：执行精确、规范化文本、语义向量和“图 + 锚点 + 程序”四级去重；
8. **泄漏检查**：按主题、图和来源集合检查跨划分污染；
9. **长度检查**：保留必要上下文，避免无关全文占满窗口；
10. **标签一致性**：规则引擎结果、自动验证结果与目标标签不得冲突。

### 7.3 独立实现复核

只用生成数据的同一份程序回放，会出现“程序自己的错误证明自己正确”的循环。正式数据至少应对关键算子建立一套独立复核实现：

- NetworkX 生成结果，使用 SciPy sparse 或 igraph 复核；
- Pandas 时间切片，使用 DuckDB SQL 复核；
- 社区结果不比较任意编号，而比较分区不变量、模块度和成员集合；
- 路径、连通性、中心性和删除节点后的变化分别做属性测试；
- 对浮点结果保存容差规则和排序并列规则。

两个实现不一致的案例不得自动进入训练集，应转入隔离区排查。

### 7.4 人工标注方案

建议的人工投入：

| 阶段 | 数量 | 标注方式 |
|---|---:|---|
| Rubric 开发 | 200 | 两人讨论并完善规则 |
| 训练集校准 | 600–1,000 | 重点覆盖边界样本和模型高损失样本 |
| Dev | 400 | 双人独立标注，分歧仲裁 |
| Final Test | 800 | 全量双人独立标注，专家仲裁 |

标注界面应隐藏数据来源方式和预期标签，避免标注者被“机器生成/人工生成”信息影响。每条样本至少判断：

- 论断是否事实正确；
- 证据是否真正支持；
- 是否过度外推或因果化；
- 当前证据是否充分；
- 四分类决策；
- 风险类型；
- 最小修订；
- 是否无法判断。

一致性目标为 Cohen's kappa 或 Krippendorff's alpha ≥ 0.70。若 `qualify` 与 `reject` 的一致性低于 0.60，应修改标注规范并重新标注，而不是删除分歧样本。

### 7.5 主动学习

首轮 SFT 后，用模型扫描未标注数据，优先提交以下样本给人工：

- 决策熵高或置信度接近阈值；
- 规则引擎与模型结论冲突；
- 多随机种子预测不一致；
- 参数扰动结果复杂；
- 模型给出过长修订或删除大量正确内容；
- 新领域上的高损失样本。

这种方式比随机追加人工标注更节省成本。

## 8. 训练设计

### 8.1 基座与训练方法

主实验建议使用 Qwen3-8B-Instruct。若许可、部署环境或中文表现验证不理想，可更换同规模的开源指令模型，但论文中必须固定基座后再开始最终数据标注。

推荐设置：

| 项目 | 配置 |
|---|---|
| 微调方式 | QLoRA，4-bit NF4 |
| 计算类型 | bf16 |
| LoRA rank | 64 |
| LoRA alpha | 128 |
| LoRA dropout | 0.05 |
| Target modules | q/k/v/o_proj，gate/up/down_proj |
| 最大序列长度 | 4,096 tokens |
| 梯度检查点 | 开启 |
| 数据 packing | 开启，但不得跨样本污染标签边界 |
| 输出约束 | JSON Schema / constrained decoding |

不建议第一版直接训练 32B 模型、做全参数微调或使用完整文章作为单条训练输入。完整图和全文应先被压缩为与当前论断相关的证据包。

### 8.2 阶段一：SFT

目标是学习任务边界、结构化输出、风险分类和最小修订。

建议初始配置：

```yaml
epochs: 2
learning_rate: 1.0e-4
lr_scheduler: cosine
warmup_ratio: 0.03
weight_decay: 0.01
max_seq_length: 4096
gradient_checkpointing: true
max_grad_norm: 1.0
bf16: true
quantization: nf4_4bit
lora_rank: 64
lora_alpha: 128
lora_dropout: 0.05
```

有效 batch size 以 token 数控制。首轮可从每次更新约 32k–64k tokens 开始，根据显存、吞吐和验证损失调整。保存每 0.25 个 epoch 的检查点，但模型选择以 Dev 集任务指标为准，不以训练损失最低为准。

### 8.3 阶段二：DPO

DPO 负责让模型偏好“最小且有证据的修订”，抑制两个常见失败模式：过度拒绝和机械加模糊词。

建议初始配置：

```yaml
epochs: 1
learning_rate: 5.0e-6
beta: 0.1
max_length: 4096
max_prompt_length: 3072
gradient_checkpointing: true
bf16: true
```

DPO 是否保留，必须通过消融实验决定。如果 DPO 仅提升拒绝率，却降低正确论断保留率或文章可读性，则应回退到 SFT，并改用规则约束或更高质量的偏好对。

### 8.4 阶段三：置信度校准

不要直接把模型生成的自然语言“confidence”当作可靠概率。应从四个决策标签首 token 的 logits 计算分布，并在 Dev 集上执行 temperature scaling。最终报告：

- Expected Calibration Error（ECE）；
- Brier score；
- risk–coverage curve；
- 不同阈值下的自动通过率与人工转交率。

部署时可设置两级阈值：高置信度 `supported/qualify/reject` 自动执行，低置信度统一转为 `abstain`。

### 8.5 为什么不先做 GRPO

第一版任务已经拥有明确标签和可构造的偏好对，SFT + DPO 更稳定、可复现且算力需求更低。只有在以下条件同时满足时再考虑 GRPO：

- 自动奖励与人工判断高度一致；
- SFT + DPO 已达到稳定基线；
- 现有错误主要来自多步修订策略，而不是标签噪声；
- 有足够资源进行奖励投机检查。

## 9. 2–4 张 RTX 4090 的资源方案

以下时间是工程估算，实际取决于序列长度分布、CPU 预处理、FlashAttention、框架版本和云服务器 PCIe 拓扑。开始正式实验前应使用 1,000 条数据跑吞吐基准。

### 9.1 两卡方案

由于 8B QLoRA 可以放入单张 24 GB 4090，两卡的推荐用法是并行实验：

| GPU | 任务 |
|---|---|
| GPU 0 | 主配置 SFT / 主随机种子 |
| GPU 1 | 消融配置、第二随机种子或数据实验 |

单次估算：

- 30k SFT、4k 上下文、2 epochs：约 12–24 小时；
- 25k–40k DPO、1 epoch：约 18–36 小时；
- 推理评测：数小时到 1 天，取决于生成长度和样本量。

完成 3 个随机种子、核心消融和失败重跑，预计需要 4–7 天连续墙钟时间。云服务器建议至少预留 2 周，给数据重生成、框架故障和评测留出余量。

### 9.2 四卡方案

推荐四张卡分别运行：

| GPU | 任务 |
|---|---|
| GPU 0 | 主配置 seed 1 |
| GPU 1 | 主配置 seed 2 |
| GPU 2 | 主配置 seed 3 |
| GPU 3 | 关键消融或超参数试验 |

这种安排通常比四卡 DDP 更适合 8B QLoRA，因为能直接提高实验并发度和统计可信度。预计 2–4 天可完成 8B 主实验与核心消融，完整项目约需 1 周 GPU 时间。

只有 8B 已明确优于强基线后，才建议用其中两张卡尝试 14B QLoRA，作为规模验证而非主线。14B 实验的目的不是替换 8B，而是回答“性能提升来自数据和方法，还是仅来自参数量”。

### 9.3 云服务器建议

- Ubuntu Linux；
- 2–4 × RTX 4090 24 GB；
- 内存至少 128 GB；
- 本地 NVMe 至少 2 TB；
- CPU 至少 32 核；
- 提前确认 GPU 间 PCIe 拓扑、散热和功率限制；
- 使用 Docker 固定 CUDA、PyTorch 和训练框架版本；
- 数据、配置、代码 commit、容器摘要和模型权重均保存哈希。

训练栈可采用 PyTorch、Transformers、PEFT、TRL、bitsandbytes，以及经过基准验证的 FlashAttention 2 或 Liger Kernel。不要在正式多随机种子实验中临时升级到未经验证的最新版依赖。

### 9.4 成本控制

云成本应拆成三部分记录：

1. GPU 训练与评测时长；
2. API 生成、改写和基线调用 token；
3. 人工标注与专家评审工时。

首轮只租足够完成 MVP 的算力。达到第 11 节的继续门槛后，再生成正式数据并扩大租用时长。

## 10. 如何通过对比实验证明模型有效

### 10.1 评测要回答什么

对比实验不能只证明“微调后的 8B 比微调前好”，因为这不足以说明新增模型对整个项目有价值。实验必须分别回答四个问题：

1. **模型是否学到了任务**：训练后是否优于同一个 8B 基座的 zero-shot 和 few-shot；
2. **创新监督是否有效**：程序轨迹、provenance 和参数扰动是否分别带来增益；
3. **是否值得替代 API 自检**：相同测试集上是否优于或接近前沿 API，同时成本和延迟更低；
4. **接入系统是否真的改善文章**：不是只在合成单句上得分，而是在真实文章中减少错误且不损害有用内容。

因此实验分成论断级、方法消融、系统级和经济性四层。只有四层证据一致，才能声称模型有效。

### 10.2 必须冻结的基线

在训练模型前，先固定同一最终测试协议下的基线：

1. Qwen3-8B-Instruct zero-shot；
2. Qwen3-8B-Instruct few-shot；
3. 现有规则校验器；
4. 当前项目使用的前沿 API 直接判断；
5. 前沿 API 自我检查；
6. API + 规则校验。

系统级对比条件：

- API 单独生成；
- API + 规则；
- API + zero-shot 8B；
- API + SFT；
- API + SFT + DPO。

### 10.3 主对比实验矩阵

所有方法使用完全相同的 Final Locked Test、相同证据包和相同输出 Schema。API 的提示词在 Dev 集冻结，不能为测试集单独调优。

| 编号 | 方法 | 目的 | 如果本模型有效，预期结果 |
|---|---|---|---|
| B0 | 规则校验器 | 衡量纯确定性规则上限 | 能抓数字错误，但较难识别语义越界 |
| B1 | Qwen3-8B zero-shot | 控制基座原始能力 | 明显弱于 SFT 模型 |
| B2 | Qwen3-8B few-shot | 排除简单提示工程即可解决 | 仍弱于 SFT 模型 |
| B3 | 前沿 API 单次校验 | 与强通用模型比较 | 专用模型至少在过度推断召回和稳定性上不差 |
| B4 | 前沿 API 自我检查 | 测试生成者自检 | 专用模型错误更少或成本明显更低 |
| B5 | API + 规则 | 当前最强非训练方案 | 新模型接入后仍能带来额外收益 |
| M1 | CiteCalibrator-SFT | 检验监督微调收益 | 显著优于 B1、B2 |
| M2 | CiteCalibrator-SFT+DPO | 检验偏好学习收益 | 修订更小、更自然，且误拒率不升高 |

主统计比较为 `M2 vs B2`、`M2 vs B4`、`API + M2 vs API + 规则`。其中最后一项是判断项目是否值得加入该模型的核心结果。

### 10.4 论断级测试怎么做

从全新主题构造 800 条双人标注金标准，四类决策和主要风险类型分层采样。每种方法只接收同样的候选论断和证据包，输出四分类、风险标签和修订文本。

主要指标：

- 四分类 macro-F1 和各类别 F1；
- `causal_overclaim`、`scope_overclaim` 等风险类型的多标签 F1；
- 过度推断召回率；
- supported 样本误拒率；
- abstain 的准确率和覆盖率；
- unsupported span F1；
- 数字和实体保留率；
- evidence ID 有效率；
- 修订后新增无支持内容比例；
- 必要限制条件覆盖率；
- ECE、Brier score 和 risk–coverage。

### 10.5 系统级盲测怎么做

单句测试只能证明分类能力，不能证明对最终文章有用。系统级实验建议从 8 个锁定主题中选择至少 40 个研究问题。对每个问题固定检索结果、图程序、证据包和初始 API 草稿，再形成以下五个版本，共得到至少 200 篇待盲评文章：

| 条件 | 生成与校验流程 |
|---|---|
| S0 | API 直接生成，不校验 |
| S1 | API 生成 → 同一 API 自检并修订 |
| S2 | API 生成 → 规则校验并修订 |
| S3 | API 生成 → zero-shot 8B 校验并修订 |
| S4 | API 生成 → CiteCalibrator 校验并修订 |

初始草稿必须完全相同，校验方法之外的温度、上下文、修订次数和后处理保持一致，避免把生成随机性或额外调用次数误当作校准效果。文章去除方法名称后随机排序，由不知道实验条件的专家评价。每篇文章至少由两人独立评审；同一研究问题的五个版本采用配对统计。

主要指标：

- 每 1,000 字过度推断数；
- 正确且被支持的原子论断数；
- 错误放行率与不必要阻断率；
- 人工转交率；
- 被修改段落比例；
- 未受影响文本的保持率；
- API 调用次数、token、成本和端到端延迟；
- 专家评分：支持性、可读性、研究效用和领域具体性。

### 10.6 如何排除“模型只是更保守”

如果模型把所有论断都拒绝，错误率会下降，但文章也会失去价值。因此必须同时报告一组相互制约的指标：

- 过度推断召回率越高越好；
- supported 误拒率越低越好；
- 正确且有支持的论断保留率越高越好；
- 修订后新增无支持内容越低越好；
- 领域信息密度和专家研究效用不能显著下降；
- 平均改动字符比例应受控。

只有“错误减少”与“正确内容基本不损失”同时成立，才算有效。正式统计采用非劣性检验约束正确论断保留率，再对过度推断率做优越性检验。

### 10.7 如何证明创新来自程序与扰动监督

其中“完整模型 vs 去掉 perturbation profile”是最关键的创新性消融。如果两者无显著差异，就不能把参数敏感性监督作为主要方法贡献。

每个消融模型除输入字段外，应使用相同基座、相同训练条数、相同随机种子和相近 token 数：

| 消融 | 移除内容 | 要验证的结论 |
|---|---|---|
| A0 | 无，完整模型 | 主模型 |
| A1 | perturbation profile | 参数扰动是否帮助识别不稳定结论 |
| A2 | provenance | 来源链是否帮助发现引用错配 |
| A3 | interpretation contract | 语义契约是否抑制因果化和实体化 |
| A4 | 仅保留事实错误训练样本 | 受控语义负例是否必要 |
| A5 | 打乱扰动标签 | 增益是否只是增加了文本字段 |
| A6 | 不做 DPO | DPO 是否改善最小修订 |

预期的定向结果是：A1 主要损害参数稳定性相关指标，A2 主要损害来源错误识别，A3 主要损害因果夸大和语义实体化识别。如果所有消融都没有定向下降，说明模型可能没有真正使用这些创新信号。

### 10.8 泛化与泄漏检查

为证明模型不是记住主题、实体或模板，需要进行：

- **跨主题测试**：Final Test 的主题完全不进入训练；
- **模板留出**：测试集使用训练阶段未出现的表达模板和人工自然改写；
- **实体替换负控**：保持结构不变、替换实体名称，检查预测是否随证据而非知名度变化；
- **证据反转测试**：只改变关键证据或扰动结果，预测应发生符合规则的变化；
- **无关证据注入**：加入表面相关但不支持结论的文献，模型不应改变正确判断；
- **真实草稿测试**：单独报告自然产生的 API 草稿，不只报告合成变异数据。

### 10.9 成本和效率比较

在相同文章集合上记录每种方案的端到端指标：

- 每篇文章的 API 调用数和 token；
- GPU 推理时间和最大显存；
- 从草稿到终稿的总延迟；
- 每 100 篇文章的估算费用；
- 转人工的论断数量；
- 每纠正一个真实错误的成本。

专用模型不一定要在所有准确率上全面击败最强 API。如果质量相当，但成本、延迟和结果方差显著下降，同样构成有价值的系统结果；若质量与成本均无优势，则没有必要部署该模型。

### 10.10 统计报告

- 主结果使用至少 3 个随机种子，报告均值和标准差；
- 按主题 bootstrap 计算 95% 置信区间；
- 配对比较以同一文章、同一论断为单位；
- 系统级专家评测应盲化条件名称并随机化顺序；
- Dev 集只用于选模型和阈值，Final Locked Test 只运行一次正式分析。

最终可以声称的结论与所需证据对应如下：

| 想声称的结论 | 必须看到的证据 |
|---|---|
| 微调有效 | M1/M2 在未见主题上显著优于 B1/B2 |
| 程序监督有效 | A0 显著优于 A1/A2/A3，且出现对应风险类型的定向下降 |
| DPO 有效 | M2 的修订质量优于 M1，supported 误拒率不恶化 |
| 优于 API 自检 | M2 或系统 S4 在质量上优于 B4/S1，或质量相当但成本显著更低 |
| 对整个项目有效 | S4 相对 S0/S2 减少真实文章错误，同时满足正确内容非劣性 |
| 具备泛化能力 | 在主题、模板和实体均未见的测试集上仍保持收益 |

## 11. 成功标准与止损条件

### 11.1 MVP 继续门槛

模型至少应达到：

- 四分类 macro-F1 比 zero-shot 8B 高 5 个百分点；
- 过度推断召回率 ≥ 0.85；
- supported 样本误拒率 ≤ 0.10；
- 数字和实体保留率 ≥ 99.5%；
- JSON 合法率 ≥ 99%；
- 修订后新增无支持论断 ≤ 1%；
- 新主题上的性能下降不超过 10 个百分点；
- 在至少一个关键指标上显著优于“API + 规则”。

### 11.2 正式系统成功标准

最终系统需要同时满足：

- API + CiteCalibrator 的过度推断显著少于 API 单独生成；
- 正确且有支持的论断数量非劣于 API 单独生成，容忍界限为 2 个百分点；
- 可读性、研究效用和领域具体性不显著下降；
- 人工审核量或 API 自检成本下降；
- 在未见主题上仍有稳定收益；
- 去掉扰动监督后性能显著下降。

### 11.3 止损条件

出现以下任一情况，应暂停扩容，优先修正任务或数据：

- SFT 无法超过 few-shot 基座；
- DPO 只提高 reject 比例，没有提高校准质量；
- 模型普遍使用“可能、一定程度上”等机械性降级；
- 自动金标签抽检错误率超过 5%；
- 新主题性能下降超过 15 个百分点；
- 混合系统无法超过 API + 规则；
- 唯一收益只是 JSON 格式更稳定；
- 独立算子实现频繁与数据生成器不一致。

此时不应继续堆数据或换更大模型，应先定位是标签定义、证据表达、输入压缩还是任务本身不可学。

## 12. 分阶段实施计划

### P0：冻结协议与基线（第 1 周）

交付物：

- ClaimCase JSON Schema；
- 标签手册与 50 个正反例；
- 主题级数据切分规则；
- 数据 lineage、哈希和版本规范；
- 所有零样本、API 和规则基线；
- frozen formal v3 与训练扩展的隔离说明。

通过条件：两名标注者对 100 条样本试标后，主要标签一致性达到可接受水平。

### P1：MVP 数据（第 2–4 周）

规模：

- 12 个训练主题、3 个开发主题、4 个测试主题；
- 1,000–1,500 个基础 ClaimCase；
- 约 8,000 条 SFT；
- 约 10,000 对 DPO；
- 300–500 条双人复核样本。

交付物：数据生成脚本、自动门禁报告、标注指南 v1 和数据卡。

### P2：试训练与决策（第 5 周）

训练一个 SFT 主模型、一个关键消融和必要的 DPO 试验。完成样本级评测和少量文章级试验，并按第 11.1 节决定是否进入正式阶段。

### P3：正式数据扩展（第 6–10 周）

扩展到 30–40 个训练主题，完成 30k SFT、25k–40k DPO 数据。使用主动学习集中人工审核边界样本，并冻结 Final Locked Test。

### P4：正式训练与消融（第 11–12 周）

完成：

- 主配置 3 个随机种子；
- 核心消融；
- 可选 14B 规模验证；
- 置信度校准；
- 完整可复现实验记录。

### P5：系统集成与盲评（第 13 周起）

接入文章生成管线，执行文章级对照实验和专家盲评，汇总质量、成本、延迟和人工转交率。

## 13. 风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 模板泄漏 | 模型识别句式而非证据 | 多模板、多 API 改写、跨主题测试、模板留出 |
| 合成文本偏差 | 真实文章效果明显变差 | 加入真实系统草稿，按来源分层评测 |
| 类别不平衡 | 全部预测 qualify/reject | 分层采样、每类指标、代价敏感阈值 |
| 过度拒绝 | 安全但无用 | DPO 最小修订偏好、非劣性约束 |
| 领域漂移 | 新学科性能下降 | 主题级留出、主动学习、领域分层报告 |
| 校验器循环论证 | 同一实现生成并验证标签 | 独立算子实现、人工仲裁、属性测试 |
| 正式实验污染 | 调参时查看最终主题 | 锁定测试集、访问记录、一次性正式运行 |
| 教师 API 依赖 | 模型只模仿某一 API 风格 | 多来源改写、程序标签为主、API 仅负责表达 |
| 修订破坏上下文 | 单句正确但段落不连贯 | 保留局部上下文、依赖图局部重写、文章级评测 |

## 14. 实验记录与可复现性

每次训练必须保存：

- Git commit 和 dirty state 摘要；
- 数据集版本、主题列表和文件哈希；
- 基座模型精确版本与许可证；
- Docker 镜像摘要、CUDA、PyTorch 和驱动版本；
- 完整超参数、随机种子和 GPU 型号；
- 训练/验证 loss、吞吐、峰值显存和总时长；
- 选择检查点和决策阈值的依据；
- 自动评测逐样本结果；
- 人工标注分歧与仲裁记录；
- 所有失败实验，而不仅是最佳结果。

## 15. 第一批可执行任务

在投入云算力前，按以下顺序推进：

1. 冻结四分类决策、风险标签和 interpretation contract；
2. 从现有六类图任务各抽取 20–30 个案例，形成约 200 条 rubric 样本；
3. 建立 ClaimCase Schema、lineage 和自动回放协议；
4. 实现至少一组关键算子的独立复核；
5. 完成双人试标，修订 `qualify` 与 `reject` 的边界；
6. 运行所有未微调基线；
7. 生成 MVP 数据并完成质量报告；
8. 租用两张 4090，先进行吞吐测试和一个 SFT seed；
9. 达到 MVP 门槛后再扩充数据、运行 DPO 和三随机种子；
10. 最后才进行 14B 验证和文章级专家盲评。

## 16. 最终决策

在当前算力条件下，最值得训练的不是“更小的文章写作模型”，而是一个对现有 Agent 系统具有独占输入优势的专用校准模型。它利用通用 API 看不到或不会稳定使用的信息——程序执行轨迹、图语义契约、来源链和参数扰动结果——形成真正的方法创新。

首要目标不是证明 8B 模型全面强于云端 API，而是证明：

> 在文献网络报告的高风险论断校验任务上，经过程序证据和扰动监督训练的 8B 专用模型，可以比直接 API 自检更可靠、更便宜、更稳定，并使最终系统获得可测量的质量提升。

如果 MVP 无法支持这项结论，应停止扩大训练规模，把论文重点保留在 Agent 工程与可执行验证；如果 MVP 达标，再将 CiteCalibrator 作为独立模型创新点纳入正式实验。
